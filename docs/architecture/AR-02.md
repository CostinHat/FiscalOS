# AR-02 — FiscalOS Architecture Re-Baseline Review

**Status:** ACCEPTED  
**Review:** AR-02  
**Scope:** Conceptual architecture re-baselining  
**Implementation impact:** Documentation only; no refactor required

## 1. Review Objective

AR-02 reviews the current FiscalOS architecture after the maturation of Classification and confirms whether the existing architectural boundaries remain valid.

The review is a conceptual architecture review. It does not authorize persistence, public API exposure, AI/NLP integration, graph infrastructure, or automatic rule generation.

## 2. Accepted Architecture

The core dependency direction remains:

```text
                    iConta
                      │
              Application / Adapter
                      │
                   Runtime
                      │
                   Domain
                      │
                 Legal Core
```

The dependency rule remains:

> Runtime may depend on Domain; Domain must not depend on Runtime.

## 3. Architectural Center Re-Baseline

The original architecture was strongly centered on Legal Reference Resolution:

```text
Legal Reference
      ↓
Resolution
      ↓
Audit
      ↓
Provenance
      ↓
Evidence
```

Classification has now matured into a first-class capability:

```text
Classification
      ↓
Classification Rule
      ↓
Evaluation
      ↓
Decision
      ↓
Explanation
```

The conceptual FiscalOS center is therefore re-baselined as:

```text
                         FISCALOS
                            │
              ┌─────────────┼─────────────┐
              │             │             │
         Legal Core   Legal Knowledge   Ingestion
              │             │             │
              └─────────────┼─────────────┘
                            │
                 ┌──────────┴──────────┐
                 │                     │
        Reference Resolution     Classification
                 │                     │
                 └──────────┬──────────┘
                            │
                    Fiscal/Legal Decision
                            │
                  Explanation / Evidence /
                    Traceability / Audit
```

This is a conceptual re-baseline, not a mandate to restructure the current codebase.

## 4. Resolution and Classification Remain Separate

AR-02 explicitly rejects merging Legal Reference Resolution and Classification.

- **Resolution** answers: which legal reference does this refer to?
- **Classification** answers: what fiscal/legal category does this belong to, and why?

They may collaborate, but they retain separate responsibilities, contracts, and evolution paths.

## 5. Assurance / Traceability

Audit, Provenance, and Evidence remain separate contracts and capabilities.

Conceptually, however, they are treated as transversal assurance/traceability infrastructure rather than as equal business verticals:

```text
Resolution ───────┐
                  ├──→ Assurance / Traceability
Classification ───┘
```

This reduces conceptual complexity without requiring deletion or immediate refactoring.

## 6. Generic Legal Core

`FiscalOS.LegalCore` remains the owner of shared structural legal primitives.

It should remain small and generic.

Examples include:

- `LegalReference`
- `ReferenceSegment`
- `JurisdictionId`
- `FullyQualifiedLegalReference`
- `SourceAuthorityLevel`
- `SpecificityLevel`

Business-specific decisions, classification outcomes, tax rules, explanations, engines, and similar concepts do not belong in Legal Core.

## 7. Ingestion Boundary

Legislation Ingestion remains a separate capability.

It must not become a mega-pipeline that combines acquisition, parsing, normalization, resolution, classification, and rule generation.

The current ingestion runtime remains a narrow, deterministic, in-memory foundation. Durable ingestion remains a future architectural capability.

## 8. Runtime and Adapter Boundary

Runtime remains the execution layer between Domain and application composition.

The iConta adapter is known technical debt: its long-term ownership belongs at an application/iConta composition boundary rather than inside Runtime.

AR-02 does not require moving it immediately.

Authorization, tenant/account/workflow context, logging, monitoring, support, and operational ownership remain outside Domain and Runtime.

## 9. Explicitly Deferred

AR-02 does not introduce or authorize:

- durable persistence
- public API exposure
- AI/NLP integration
- graph infrastructure
- automatic rule generation
- broad runtime redesign
- immediate adapter relocation

## 10. Decision Table

| Area | AR-02 Decision |
|---|---|
| Domain → Runtime dependency | **REJECT** |
| Runtime → Domain dependency | **KEEP** |
| Generic Legal Core | **KEEP** |
| Legal Reference Resolution | **KEEP** |
| Classification | **ELEVATE to core capability** |
| Resolution + Classification merge | **REJECT** |
| Ingestion as separate capability | **KEEP** |
| Audit / Provenance / Evidence contracts | **KEEP** |
| Audit / Provenance / Evidence as equal business verticals | **RE-FRAME as transversal assurance/traceability** |
| iConta adapter currently in Runtime | **ACCEPT temporarily; debt recorded** |
| Persistence / API / AI / NLP / Graph / Rule generation | **DEFER** |

## 11. Architectural Baseline

FiscalOS is the internal engine of fiscal/legal knowledge, referencing, and deterministic fiscal/legal decision-making that iConta can use as a platform capability.

FiscalOS is not currently:

- a public API product;
- a standalone end-user application;
- a full durable legislation storage system;
- an AI/NLP product;
- a graph database;
- an automatic rule generator.

## 12. Acceptance

**AR-02 is accepted and closed.**

No refactor is required solely because of AR-02.

Future implementation work should use this re-baselined architecture as the reference point and intervene only when a concrete milestone violates these boundaries.
